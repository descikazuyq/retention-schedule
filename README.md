# 本地保管期限与销毁清册

这是一个在本机运行的本地保管期限与销毁清册。只登记条目元数据，不读取或保存真实文件。

## 使用

```bash
go test ./...
```

调用者先选择一个本地保存位置并打开，然后即可办理各项业务：

```go
s, _ := retention.Open("/path/to/vault")
defer s.Close()

s.Register(retention.RegisterInput{
    ID: "A-001", Category: "合同",
    Start: retention.MustParseDate("2020-01-01"),
    End:   retention.MustParseDate("2025-01-10"),
})

s.Freeze(retention.FreezeInput{
    ArchiveID: "A-001", FreezeID: "F-1",
    Reason: "诉讼", FrozenOn: retention.MustParseDate("2025-01-08"),
})
s.Release(retention.ReleaseInput{
    ArchiveID: "A-1", FreezeID: "F-1",
    Reason: "结案", ReleasedOn: retention.MustParseDate("2025-01-09"),
})

// 销毁前可先只做核对：不销毁、不生成清册、不占用申请编号。
r, _ := s.Check(retention.CheckRequest{
    ApplicationID: "APP-2",
    ProcessedOn:   retention.MustParseDate("2025-01-10"),
    ArchiveIDs:    []string{"A-001"},
})
switch r.Status {
case retention.CheckReady:       // 可以办理
case retention.CheckBlocked:     // 存在阻碍，见 r.Results
case retention.CheckReplayable:  // 可以取回原清册，见 r.Manifest
case retention.CheckConflict:    // 申请编号冲突，r.Manifest 附原清册
}

m, err := s.Destroy(retention.DestructionRequest{
    ApplicationID: "APP-1",
    ProcessedOn:   retention.MustParseDate("2025-01-10"), // 截止日当天即到期
    ArchiveIDs:    []string{"A-001"},
})
_ = m

h, found, _ := s.History("A-001") // 登记内容、全部冻结解除历史、销毁状态与清册
_, found, _ = s.GetManifest("APP-1")
```

## 规则要点

- 日期统一 `YYYY-MM-DD`，按日历日期比较，不受时区或夏令时影响；日期必须真实存在。
  年、月、日分别恰好是四位、两位、两位半角数字（0-9），分隔符必须是半角横线，
  年份范围 0001-9999，闰年沿用公历规则（2000-02-29 有效，1900-02-29 无效）。
  带正负号、缺少补零、首尾空白、附带时间，或直接把反斜杠转义文本传给 ParseDate
  （例如 `2025-+1-10`、`2025-01-+1`）都明确返回可由 ErrInvalidDate 识别的错误，
  不会通过去空白、补位、去掉符号或解释转义接受。读取保存记录中的 JSON 日期字符串时，
  以字符串解码后所表示的实际文本判断：普通字符与 Unicode 转义可以混用，
  `"\u0032025-01-10"` 与 `"2025-01-10"` 是同一个日期，解析结果与输出都为
  `2025-01-10`，档案历史、清册与到期判断（截止日当天即到期）都不因转义写法变化；
  转义后出现加号、空白等非法字符，或日期写成数字、对象、null 等非字符串值，都按
  保存记录损坏拒绝打开（ErrCorruptState），原保存内容保持原样。字段原本允许缺省或
  为 null 的含义不变（未解除冻结可以没有解除日期；必填日期缺失、为 null 仍按既有
  缺项规则判损坏）。给一个已有日期解码非法值时解码失败并保留原日期。
- 登记：编号、类别不可空白；截止日不能早于起算日；重复编号明确失败且不影响已有记录。
  读取保存记录时还会核对档案身份：保存的档案集合中，用于查找每份档案的编号和该份
  登记内容里的 id 必须都非空白，并且是同一个编号。登记内容的 id 缺失、为 null、为空串
  或只有空白，或者两处写了不同编号（包括仅大小写或首尾空白不同），都属于保存记录损坏，
  打开保管库返回 ErrCorruptState，不交付可继续办理的保管库；错误说明是档案编号不一致
  （给出查找编号与记录内编号）还是缺少有效编号（指出对应的查找编号与缺失位置）。比较以
  JSON 解码后的实际文本为准，转义写法不同但解码后相同的编号仍合法；不能通过去空白、
  改号或补写缺失编号修复保存内容，正常登记时对输入去首尾空白的行为继续保留。这条规则
  适用于尚未销毁、被冻结和已销毁的档案，合法的期限、修订历史或清册归属不能掩盖编号矛盾，
  原保存内容保持原样。保管库打开后保存内容才出现这种问题的，下一次使用有效输入查询历史、
  取回清册、销毁前核对或办理业务（含操作另一份正常档案）同样按整库记录损坏失败，不返回
  正常历史、清册或部分报告，不改变档案状态或生成清册；编号一致的记录继续沿用现有功能，
  没有修订信息的旧档案仍可按已有规则读取。
  读取保存记录时同样核对档案编号唯一：保存的档案集合中只要同一编号出现两次，
  即使两份内容完全相同（类别、日期、冻结与修订历史一致），或两份内容不同，都不能
  合并、忽略，也不能根据哪份期限更长、哪份仍被冻结挑选可信记录，一律按保存记录损坏
  拒绝打开（ErrCorruptState），错误指出重复的档案编号并说明登记重复，原保存内容保持
  原样。编号按 JSON 字符串解码后的实际文本识别，直接写出的 A-1 与通过 Unicode 转义
  写出的同一编号仍算重复；不同编号各自登记一次不受影响，不同档案登记内容中出现相同
  字段名属于正常保存格式，不会误判为编号重复。保管库打开后保存内容才出现重复的，
  下一次使用有效输入查询历史、取回清册、销毁前核对或正式办理时（含操作另一份正常
  档案）同样报整库记录损坏，不返回正常历史、清册或部分报告，不写入新记录、不改变
  销毁状态或生成清册，原保存内容保持原样。没有重复编号的保存内容继续按已有规则使用，
  包括没有修订信息的旧档案。
  同一份保存记录的最外层最多只能出现一次档案集合：普通读取对同名字段只保留最后一个
  值，最外层写了两次 archives 时，前一次的档案集合会被后一次整批替换——第一处保存着
  未解除诉讼冻结的档案，第二处保存成没有冻结的同号档案，读取后就可能被判为可以销毁。
  因此最外层出现两次或更多次档案集合时，打开保管库必须返回可由 ErrCorruptState 识别
  的错误，不交付可以查询或办理的保管库；错误说明重复的是档案集合 archives，而不是误报
  某个档案编号重复。两处集合内容完全一致、只含不同编号、其中一处为空对象或 null，都按
  同一规则拒绝，不能合并、择取最后一份，也不能按哪份保留了更多冻结来选记录；调整两处
  的保存顺序不能改变拒绝结果。字段名按 JSON 字符串解码后的实际文本识别，转义后表示
  同一字段名的写法也算重复；现有能识别为档案集合的大小写写法单独出现时继续可读，混用
  它们重复保存同样失败。这条限制只针对最外层的档案集合字段：不同档案的登记内容中各自
  带有 id、日期和冻结字段是正常格式，不因字段名相同被误判。保管库打开后保存内容才出现
  这种重复的，下一次使用有效输入查询历史、销毁前核对或办理业务（含操作另一份没有问题
  的档案）同样按整库记录损坏失败，不返回部分历史或可以办理的结论，不改变档案状态、
  生成清册或重新保存来消除重复，原保存内容保持原样。档案集合缺省或仅一次为 null 的
  空库兼容行为不受影响。
- 冻结：同一档案可有多条，冻结编号同档案内唯一；解除必须填日期和原因，解除日期不早于冻结日期；
  解除只做标记，记录全部保留；不能给不存在或已销毁的档案新增冻结。
  读取保存记录时同样核对编号唯一性：一份档案的全部冻结历史中一个冻结编号只能出现一次，
  解除过的记录仍占用原编号。只要同一档案保存了两条相同编号的冻结——两条都未解除、一条已解除
  而另一条未解除，或两条均已解除，即使原因、日期和解除信息完全一致也不能合并成一条——即使该档案
  已销毁且所属清册、期限和处理日期都正确，都按保存记录损坏拒绝打开（ErrCorruptState），错误指出
  档案编号与重复的冻结编号，不合并、不挑选、不改编号、不删除或自动解除重复记录；唯一性只限定在
  同一份档案内，不同档案各有一条同编号冻结仍是合法情况，解除其中一份不影响另一份。保管库打开后
  保存内容才出现重复的，下一次使用有效输入查询历史、取回清册、销毁前核对或办理业务（含操作另一份
  正常档案）同样报整库记录损坏，不返回正常历史、清册或部分核对报告，不产生业务变更，原保存内容
  保持原样。
  读取保存记录时同样核对每条冻结保留的原始信息：与办理冻结时的要求一致，每条冻结都必须带有
  非空白的冻结原因和有效的冻结日期。保存记录中的冻结原因缺失、为 null、为空串或仅含空白都算
  缺少原因；冻结日期字段缺失或为 null 都算缺少日期（已填写的日期仍须是真实的 YYYY-MM-DD
  日期）。命中任一缺项都按保存记录损坏拒绝打开（ErrCorruptState），错误指出档案编号、冻结编号
  以及缺少的是冻结原因还是冻结日期，两项同时缺少时两项都说明。这条要求覆盖未解除与已解除的
  全部冻结历史，也覆盖已销毁档案的冻结：解除日期与解除原因保存得再完整，也不能拿解除日期代替
  冻结日期、拿解除原因补齐冻结原因，清册归属、条目与处理日期都正确同样不能掩盖缺项；不自动
  补写日期或原因、不删除冻结、不更改解除状态。保管库打开后保存内容才出现缺项的，下一次使用
  有效输入查询历史、取回清册、销毁前核对或办理业务（含操作另一份正常档案）同样报整库记录损坏，
  不返回部分历史、部分核对报告或正常清册，也不借办理操作把内容重新保存，原保存内容保持原样。
  没有冻结的档案不受影响；新增冻结时对原因去除首尾空白的既有行为保持不变。
  读取保存记录时还会核对冻结状态与销毁记录：仍被冻结的档案不能销毁，销毁后的历史也遵守这条
  规则。档案已标记为已销毁、所属清册存在，清册归属、条目内容和处理日期都合法，但该档案仍有
  一条冻结标记为未解除时，即使其他冻结已经解除、即使这条记录残留了解除日期或解除原因，也按
  保存记录损坏拒绝打开（ErrCorruptState），错误指出档案编号、未解除的冻结编号和所属清册申请
  编号；解除与否只沿用保存的解除标记判断，残留的解除日期、原因不能当作已解除。一份清册收录
  多份档案时任一份存在这种矛盾即整库不可读，不返回其余正常档案的记录，也不自动解除冻结、
  删除冻结历史、修改销毁标记或重建清册来消除冲突。保管库打开后保存内容才出现这类矛盾的，
  下一次使用有效输入查询历史、取回清册、销毁前核对或办理业务（含操作不在该清册中的档案）
  同样报整库记录损坏，不返回正常历史、清册或部分核对报告，不产生业务变更，原保存内容保持
  原样。尚未销毁的档案保留未解除冻结仍是合法状态，可正常查看并在销毁前核对中显示冻结阻碍；
  已销毁档案没有冻结，或全部冻结均已合法解除时，历史和清册继续完整可查。
- 修订：尚未销毁的档案（含被冻结的）可延长或缩短保管截止日，不必重新登记，编号、类别、起算日不变；
  新截止日不早于起算日且不等于原截止日。首次办理时所提交的原截止日必须与当前保存值一致，
  否则返回期限已变化错误并附当前截止日。修订编号全库唯一、与销毁申请编号互不占用；
  同编号同内容重试取回首次记录，改任何一项即编号冲突；失败不留历史，失败编号可再提交。
  打开保存位置时还会核对已保存历史：每个成功修订编号只能对应一条保存的修订记录，
  同一档案历史中重复编号、不同档案保存同号修订（即使内容相同）或编号与已关闭清册
  申请编号相同，都按保存记录损坏拒绝打开（ErrCorruptState），不合并、不挑选记录；
  保管库打开后保存内容才出现此类冲突的，下一次查询、核对或办理同样报记录损坏，
  冲突属于整库且原保存内容保持原样，不自动改编号、删除历史或重建清册。
  打开保存位置时还会核对每条修订保留的办理信息：与提交修订时的要求一致，每条
  已保存修订都必须带有非空白的修订原因和有效的修订日期，历史才能说明这次调整是
  在何时、因何办理的。保存记录中的修订原因缺失、为 null、为空串或仅含空白都算
  缺少原因；修订日期字段缺失或为 null 都算缺少日期（已填写但不是真实
  YYYY-MM-DD 日历日期的，继续按保存记录损坏处理）。命中任一缺项都按保存记录
  损坏拒绝打开（ErrCorruptState），错误指出档案编号、修订编号以及缺少的是修订
  原因还是修订日期，同一条修订同时缺少原因与日期时两项都说明。这项要求覆盖全部
  成功修订，不只检查最后一条：一份档案先延长期限、随后又缩短，中间那次修订没有
  原因，不能因为最终截止日合法、全部期限前后衔接就接受它。被冻结或已销毁档案的
  修订历史也遵守同一要求；销毁清册的归属、条目和处理日期都正确，仍不能掩盖修订
  信息缺失。绝不补写原因、借用冻结或销毁日期，也不删除那次修订来继续使用。
  保管库打开后保存内容才出现缺项的，下一次使用有效输入查询历史、销毁前核对或
  办理业务（含操作另一份正常档案）同样按整库记录损坏失败，不返回正常历史或部分
  核对结果，不产生业务变更，原保存内容保持原样。没有修订记录的旧档案继续沿用
  现有兼容行为，不因不存在修订原因和修订日期而被拒绝。
  已关闭清册中的每条档案条目是销毁成功那一刻的登记内容快照，其类别、起算日和
  截止日必须与对应档案保存的登记内容逐项一致：截止日取销毁时最终生效的期限
  （最后一次成功修订的新截止日，没有修订时为最初登记的截止日），即使修订历史
  衔接完整、清册归属正确，清册保存成最初登记的截止日（延长、缩短或改回早先用过
  的日期均同此规则，不按修订办理日期重新挑选）也按保存记录损坏拒绝，错误指明
  清册申请编号、档案编号与不一致的项目；一份清册收录多份档案时任一条目矛盾即
  整库不可读，不挑选可信记录，也不能靠覆盖清册、修改档案或删除记录消除差异。
  保管库打开后保存内容才出现这类差异的，下一次使用有效输入查询、销毁前核对或
  办理业务同样报整库记录损坏，不返回正常历史、清册或部分报告，不产生业务变更，
  即使本次操作的档案不在那份清册中也一样，原保存内容保持原样。
  已关闭清册还必须带有处理日期，且处理日期不能早于任一条目档案销毁时最终生效
  并保存到清册里的截止日——沿用办理销毁时同一条到期规则（截止日当天即到期）：
  缺少处理日期（缺失或为 null）不能当作已经办理的销毁日期，按保存记录损坏拒绝
  打开，错误指出申请编号；处理日期早于所收录任一档案的截止日属于提前销毁，即使
  该档案标记为已销毁、清册归属与条目快照都一致，也按保存记录损坏拒绝，错误同时
  指出申请编号、档案编号、处理日期和截止日。期限修订过的档案按清册条目保存的
  最终截止日判断（延长、缩短或改回早先用过的日期都一样），不按修订办理日期重新
  挑选另一版期限。一份清册收录多份档案时任一份未到期即整库不可读，不返回其余
  已到期档案的正常记录，也不略过未到期条目，不通过补处理日期、改期限、改销毁
  标记或清册条目消除矛盾。保管库打开后保存内容才出现此类问题的，下一次使用有效
  输入查询历史、取回清册、销毁前核对或办理业务（含操作不在该清册中的档案）同样
  报整库记录损坏，不返回正常结果或部分核对报告，不产生业务变更，原保存内容保持
  原样。合法清册在截止日当天或之后处理，历史与清册保持完整可查。
  打开保存位置时还会核对整段期限历史：最初截止日以及每条修订中的原截止日、
  新截止日均不得早于同一档案的起算日——登记与修订办理时都不可能保存早于
  起算日的截止日，只核对当前期限合法、修订前后衔接仍有缺口。当前截止日
  合法、修订完全衔接，中途却曾把期限缩短到起算日之前、随后又改回合法
  日期的历史（例如起算日 2020-01-01，最初截止日 2025-01-10，第一条修订
  缩短到 2019-12-31，第二条再延长到 2026-01-10），即使最后改回合法日期也按
  保存记录损坏拒绝打开（ErrCorruptState）；最初截止日本身早于起算日、后来
  通过修订改到合法日期的情形同样如此。错误信息指出档案编号、出错的期限
  位置（最初截止日或某条修订的原截止日/新截止日）、该截止日与起算日，
  问题在修订记录中时同时指出修订编号。尚未销毁和已经销毁的档案都适用，
  即使已关闭清册的条目、归属和处理日期正确，也不能掩盖历史中的非法期限；
  绝不删除出错的修订或把历史日期改成当前截止日。保管库打开后保存内容才
  出现此类历史期限错误的，下一次使用有效输入查询、销毁前核对或办理业务
  （含操作另一份正常档案）同样报整库记录损坏，不返回正常历史、清册或部分
  核对报告，不产生业务变更，原保存内容保持原样。截止日等于起算日合法，
  合法的缩短、延长和改回早先用过的期限继续可用；没有修订记录的旧档案
  缺少最初截止日时，仍按登记截止日补齐。
  历史核对同时给出最初截止日、当前截止日和按成功顺序排列的全部修订记录。
- 核对：销毁前的只读核对，一次看清整批所有阻碍。申请编号尚未成功使用时，按提交顺序逐份给出
  类别、起算日、截止日、销毁状态和全部适用阻碍（不存在、已销毁、未到期、仍有未解除冻结，可逐一识别）；
  未到期与多条未解除冻结并列显示，每条冻结带编号、原因和冻结日期；已销毁档案附所属清册申请编号与处理日期；
  全部无阻碍才显示可以办理。申请编号已成功使用时，日期与档案集合相同（顺序无关）显示可以取回原清册，
  改变日期或集合则显示申请编号冲突，二者均附原清册。空白编号/日期、空名单、重复编号或读取记录失败时
  整次核对明确失败，不返回部分报告。
- 销毁：一次可多选；只有全部存在、到期、未销毁、无未解除冻结时才整体成功并生成已关闭清册，
  清册条目按关闭瞬间的登记内容保存类别、起算日和当时最终生效的保管截止日。
  空名单、名单重复或任一不符条件时整次失败，不留部分销毁或清册。
  读取保存记录时同样核对申请编号唯一：已成功的销毁申请只能对应一份已关闭清册，保存的
  清册集合中只要同一申请编号出现两次，即使两份清册完全一致（处理日期、条目与归属都相同），
  或两份收录相同档案但处理日期不同、且两个日期都满足到期规则，都不能以后一份覆盖前一份，
  也不能按处理日期或收录档案挑选其中一份，一律按保存记录损坏拒绝打开（ErrCorruptState），
  错误指出重复的申请编号并说明该编号对应多份清册，拒绝结果与两份记录的保存顺序无关，原保存
  内容保持原样。编号按 JSON 字符串解码后的实际文本识别，直接写出的 APP-1 与通过 Unicode
  转义写出的同一编号仍算重复；不同申请编号各自对应一份清册不受影响，不同清册记录内部带有
  处理日期、条目、档案编号等同名字段属于正常保存格式，不会误判为申请编号重复。这种重复保存
  不是正常的申请重试：相同日期和档案集合的重试只取回唯一的原清册，绝不会产生两份记录。
  保管库打开后保存内容才出现重复的，下一次使用有效输入查询历史、取回清册、销毁前核对或办理
  业务时（含操作另一份正常档案或正常清册）同样报整库记录损坏，不返回正常历史、清册或部分
  核对报告，不销毁、不生成清册或产生其他业务变更，不合并重复清册，也不删除、改号或重新生成
  清册，原保存内容保持原样。
  读取保存记录时还会核对清册身份：保存的清册集合中，用于找到每份清册的编号和该份
  清册内容里的 application_id 必须都非空白，并且是同一个编号。清册内容的 application_id
  缺失、为 null、为空串或只有空白，或者两处写了不同编号（包括仅大小写或首尾空白不同），
  都属于保存记录损坏，打开保管库返回 ErrCorruptState，不交付可继续办理的保管库；错误
  说明是申请编号不一致（给出查找编号与清册内容里的申请编号两处各自保存的编号）还是缺少
  有效编号（指出对应的清册记录，并说明缺的是查找编号还是清册内容中的申请编号）。比较以
  JSON 解码后的实际文本为准，转义写法不同但解码后相同的编号仍合法；不能通过去空白、用
  查找编号补写清册、以清册内容改号或删掉冲突记录修复保存内容，正常提交时对申请编号去首尾
  空白的行为继续保留。这条规则适用于所有已关闭清册，即使档案已经销毁、归属关系正确、
  条目快照与处理日期都合法、期限修订完整，其他校验全部通过，也不能把编号矛盾的清册当成
  正常记录。保管库打开后保存内容才出现这种问题的，下一次使用有效输入查询历史、取回清册、
  销毁前核对或办理业务（含查询、操作另一份正常档案或另一份正常清册）同样按整库记录损坏
  失败，不返回正常历史、清册或部分核对报告，不写入业务变更；编号一致的清册继续沿用现有
  功能，合法清册仍可通过历史查询、按编号取回和相同申请重提得到原内容。
- 幂等：已成功的申请以相同日期和档案集合（顺序无关）重放返回原清册；沿用编号改日期或集合则失败；
  失败的申请条件改变后可用同编号重试。
- 并发：多个本机程序同时办理时以文件锁决定先后，先成功的冻结挡住销毁，先成功的销毁挡住后续冻结。
  核对在共享锁内读取同一已保存状态，一份报告不会混入操作前后的不同结果；核对之后状态若变化，
  正式提交仍按最新状态判断。
